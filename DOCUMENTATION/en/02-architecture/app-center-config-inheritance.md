# App Center — Q180/Q220 Configuration Center inheritance and immutable policy

[Français](../../fr/02-architecture/app-center-config-inheritance.md) · [General Configuration Engine](configuration-engine.md) · [QA](../13-tests-quality/app-center-configuration-gates.md) · [Approved Q171–Q220](../00-project-control/decisions-q171-q220.md)

**Status: SPECIFIED CANDIDATE / NOT INTEGRATED / QA RUNTIME PLANNED.** Q180 D and Q220 D approved an administrable, versioned Configuration Center with inherited policy, rule simulation, RBAC, change history and recovery. The exact default settings, numeric thresholds, per-role editing scopes, schema and rule language remain **open technical choices**. This document does **not** establish an implemented Configuration Center or grant any configuration operation.

## One authority per rule, and a restrictive inheritance model

| Order | Scope | Typical intended owner | Constraint |
|---|---|---|---|
| 0 | Product-level hard invariants | Reviewed Core software contract | Cannot be edited or disabled by any configuration scope |
| 1 | Global policy | Authorized FORGE server administrator | Constrained by hard invariants and host qualification |
| 2 | Server | Authorized administrator for identified host | Cannot widen global policy or physical limits |
| 3 | Organization | Authorized organization authority | Cannot override parent safety/RBAC, must follow server ownership |
| 4 | Hosting plan | Administrator with plan authority | Quotas/allowed engines narrowed or delegated under upstream policy |
| 5 | Site/application | Authorized site owner within owning organization | May narrow limits and disable eligible features, never create a bypass |

The existing general Configuration Engine also anticipates *account* and permitted per-user **presentation preferences**. Q180's abbreviated chain does **not erase** those prior capabilities: adding a new account/user scope needs explicit specialist rules. In particular, a user override must not re-enable containers denied at server/plan level or change hard quotas. This prototype deliberately models **only the five approved Q180 scopes**.

**Important:** the owner-defined FORGE `/forge:8447` and PANEL `/panel:8446` paths/ports and automatically detected machine IP/verified existing FQDN are **system portal access policy**, not a customizable portal domain field. Tenant **website domains** and Q5/Q55 **one brand per organization** are separate administrative features subject to DNS/TLS, roles and contracts. Any older "configurable system portal hostname" text requires targeted reconciliation, not a new subdomain automatically generated by Configuration Center.

## Config families and non-negotiable constraints

The [candidate offline policy resolver](../../../scripts/preview_app_center_inheritance.py) recognizes a **tiny illustrative allowlist**, not a complete product registry:

- `app.native.allowed`, `app.container.allowed`, `app.catalog.verified_partner_allowed`: restrictive booleans (a lower scope may turn a permitted feature **off**, never turn it back on against a parent).
- `app.container.max_cpu_millicores`, `app.container.max_memory_mib`, `app.container.max_pids`: tightening ceilings (a child may lower, never increase). Actual OS capacities/driver quotas require trusted measurement and revalidation, not a local JSON field.
- Immutable demonstration gates: `app.native.premium_required=false`, `app.native.container_runtime_required=false`, `app.core.hub_required=false`, `app.security.generic_shell_allowed=false`, `app.security.tenant_isolation_required=true`, `app.security.signed_artifacts_required=true`, `app.container.privileged_by_default=false` and reserved control-panel ports **8446/8447**.

These invariants explain policy, not a substitute for Linux cgroups, signed package checks or server-side authorization. Real system hard caps, prohibitions on privileged Docker socket/mounts and consent rules must apply even if an administrator requests an override. The engine is not allowed to interpret user-entered expressions, arbitrary scripts or shell hooks.

## Read-only candidate preview — synthetic example

The [fictional JSON policy fixture](../../../evidence/app-center-fixtures/config-inheritance.synthetic.json) illustrates global→site restrictions with arbitrary QA numbers **not adopted as product defaults**. A global CPU ceiling in that synthetic file is narrowed by server, organization, plan and site, while the plan disables container access. A site-level attempt to re-enable it or enlarge the quota is rejected rather than silently accepted.

```sh
python3 scripts/preview_app_center_inheritance.py --fixture app-center
python3 tests/documentation/test_app_center_inheritance.py -v
```

The output exposes a per-key **provenance trail** (the source scope and illustrative value), the fictional effective value and immutable invariants. It **always** reports `policy_status=SYNTHETIC_CANDIDATE_ONLY`, `authorization_verified=false`, `policy_signature_verified=false`, `physical_capacity_verified=false`, `audit_written=false`, `resource_reservations_created=false`, `execution_allowed=false` and `apply_available=false`.

The Python tool reads one bundled fixture only, runs no SQL or network, cannot change Linux or a PHP site, cannot issue a job and cannot read production secrets. Fixture acceptance is **not** an approval to modify settings. The demo "allowed" flags do not prove actual Docker/Podman compatibility or actor permission.

## Proposed future Configuration Center UX

**FORGE** shows a setting's inherited source, effective value, allowed editor, impact, server capabilities, affected organizations/sites, policy diff, rejected proposals, history and rollback/compensation status. **PANEL** shows only site/account options already delegated by the parent policy and never exposes host/global controls. A shared settings UI can render both spaces, but the server-side authorization remains separate.

Configuration dimensions requiring eventual specialist catalogs include native installer versions/certification, local catalog source/cache/signatures, Docker vs Podman per host, CPU/RAM/PIDs/image and volume quotas, network exposure, WAF detect/block policies, AV scanners/quarantine, staged upgrades, retention, issuer/secret references, notification destinations and optional sponsored catalog placement. **No arbitrary prices, vendors, thresholds, retention days or default enabled-state are set by this candidate.** A free native installer is not a promise every third-party commercial app is free.

Changes that affect Linux or customer data follow Q47 **DRAFT → PLAN/DIFF → PREFLIGHT → SNAPSHOT → APPLY → VERIFY → COMMIT/RECOVER**, with actor/scope checks and auditable revisions. A UI simulation must never call APPLY. Privileged effects require narrowly typed Go operations; no `shell.exec`/arbitrary command. Concurrency, stale revisions, locking and durable jobs belong to independently approved API/IPC and DB contracts.

## Review / evidence status

The [offline regression tests](../../../tests/documentation/test_app_center_inheritance.py) exercise narrowing, immutable keys, bad types, forged scopes, inconsistent chains and no-apply flags. The [separate runtime acceptance matrix](../13-tests-quality/app-center-configuration-gates.md) remains **PLANNED / NOT EXECUTED**. Before implementation: Security reviews invariant enforcement and tenant isolation; API/IPC signs off on typed read/plan/apply/recover contracts; Database approves versioned schemas and transactions; QA qualifies genuine Symfony/Go/host operations and recovery, following R1–R4 prerequisites.

**Core is authoritative for tenant runtime policies. Private Hub may administer only its own publisher-side catalog/offers/consent policies and cannot push configuration to bypass Core limits, make One-Click require a commercial entitlement, or access Linux privileges.**
